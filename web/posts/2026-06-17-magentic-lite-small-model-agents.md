## 한 줄 요약
> 마이크로소프트 리서치가 '작은 모델도 설계가 맞으면 충분하다'는 것을 코드와 수치로 증명했다.

## 리드 — 왜 지금 이게 중요한가?

AI 에이전트 경쟁이 '더 큰 모델'로만 흐르는 동안, 마이크로소프트 리서치는 반대 방향을 택했다. 14B 파라미터(매개변수 — 모델의 지식·추론 능력을 담는 단위)짜리 오케스트레이터와 9B짜리 브라우저 에이전트를 조합해 실제 웹 작업 자동화 시스템 MagenticLite를 완성한 것이다. 이 시스템은 레스토랑 예약, 경비 폼 작성, 파일 정리 같은 실무 작업을 사람 개입 없이 처리하며, 코드와 모델 모두 연구 커뮤니티에 공개됐다.

## 배경 — 기존에는 어땠나?

AI 에이전트를 만들려면 통상 두 가지 선택지가 있었다. 첫 번째는 GPT-4급 대형 모델을 클라우드에서 돌리는 방식 — 성능은 좋지만 비용과 데이터 프라이버시 문제가 따라온다. 두 번째는 소형 모델을 직접 사용자 기기에서 돌리는 방식 — 비용은 낮지만 복잡한 멀티스텝 작업에서 성능이 뚝 떨어진다.

특히 "몇십 개 단계를 거쳐 형식을 채우고, 로그인하고, 조건에 맞는 정보를 골라 예약까지 완료하는" 실제 업무에서 소형 모델은 중간에 흐름을 잃는 문제가 반복됐다. 벤치마크에서 괜찮아 보이는 모델도 실제 사이트에 붙여놓으면 바로 한계가 드러났다.

마이크로소프트 리서치 팀이 세운 가설은 이랬다. "에이전트 능력은 지식 크기가 아니라 도구 오케스트레이션(여러 도구를 계획적으로 조율하는 능력)에서 나온다."

## 핵심 — 무엇이 다른가?

MagenticLite는 세 개의 구성 요소가 역할을 나눠 맡는 구조다.

**MagenticBrain** — 14B 파라미터의 오케스트레이터. 사용자 요청을 받아 단계별 계획을 세우고, 코딩·터미널 명령을 직접 실행하거나 Fara1.5에 브라우저 작업을 위임한다. Qwen 3 14B를 기반으로 훈련됐다.

**Fara1.5** — 웹 브라우저 조작에 특화된 모델. 4B, 9B, 27B 세 가지 크기로 제공되며 팀이 권장하는 크기는 9B다. 이전 버전인 Fara-7B 대비 OnlineMind2Web 벤치마크(실제 웹 작업 300개로 구성된 평가 기준)에서 성능이 약 2배 향상됐다. 27B 버전은 같은 벤치마크에서 90% 이상의 성공률을 기록했다.

**MagenticLite 앱** — 두 모델을 연결하는 실행 환경. 브라우저와 로컬 파일시스템을 하나의 흐름 안에서 제어한다.

| 구분 | 기존 방식 | MagenticLite |
|------|---------|-------------|
| 모델 크기 | 수백B 파라미터 클라우드 모델 | 14B + 9B 소형 모델 조합 |
| 데이터 위치 | 클라우드 전송 필요 | 사용자 기기 내 처리 가능 |
| 장기 작업 | 중간에 흐름 손실 | 수백 단계 컨텍스트 유지 |
| 중요 순간 처리 | 자동 진행 또는 전면 차단 | Critical Point만 사용자 확인 |

특히 "Critical Point(임계 지점)" 메커니즘이 흥미롭다. 마치 비행기 조종사가 이착륙 때만 집중 점검하는 것처럼, 결제·로그인·제출 같은 되돌리기 어려운 순간에만 사용자 확인을 요청하고 나머지는 자율 처리한다. 폼 작성 같은 반복 작업에서 과도하게 개입을 요청하던 이전 버전의 문제를 해결한 것이다.

## 시장 영향 — 어디에 쓰이나?

- Fara1.5-27B: OnlineMind2Web 300개 작업에서 90% 이상 성공률
- Fara1.5-9B: 동급 파라미터 모델 중 SOTA(최고 성능 기준) 달성
- 지원 작업: 경비 정산 폼 작성, 레스토랑 예약, 요리법 재료 가격 비교, 로컬 파일 정리

코드는 GitHub에, MagenticBrain과 Fara1.5 모델은 Microsoft Foundry 플랫폼에 공개됐다. 보안을 위한 샌드박스 도구 Quicksand도 오픈소스로 함께 공개됐다. 실제 사용자 기기에서 직접 실행 가능한 구조라 기업 환경에서 민감한 데이터를 클라우드로 보내지 않아도 되는 점이 엔터프라이즈(기업용) 시장에서 차별점이 될 수 있다.

## 병규의 한 줄

이번에 흥미로운 건 수치보다 설계 철학이다. '더 큰 모델이 더 나은 에이전트'라는 암묵적 가정을 깨고, 역할 분리·데이터 파이프라인·컨텍스트 관리라는 공학적 선택이 모델 크기를 대체할 수 있음을 보여줬다.
